Monitoring Windows and macOS endpoints with Wazuh

How I deployed Wazuh SIEM in Docker, enrolled real laptops, and proved it works by triggering and investigating an alert.

Role it supports
SOC Analyst, DevSecOps
Setting
Lab with real laptops
Tools
Wazuh 4.9, Docker, Ubuntu, UFW, Microsoft Defender

The problem

A small company with Windows and macOS laptops usually has antivirus on each machine but no single place to see what is happening across all of them. If someone tries to guess a password on three laptops in one evening, nobody notices. I wanted one dashboard that collects security events from every endpoint, flags suspicious activity, and lets me compare what a SIEM sees with what Microsoft Defender reports.

What I built

I ran Wazuh's manager, indexer and dashboard as Docker containers on one Ubuntu 22.04 host, and enrolled a Windows 11 laptop and a macOS laptop as agents. Only the dashboard is open to my browser. The agents talk to the manager on two dedicated ports.

What it runs on: an Ubuntu 22.04 VM with 4 CPU cores, 8 GB RAM and 50 GB disk, Docker Engine with the Compose plugin, and the two laptops on the same network.

How I did it

  1. Prepared the host

    The Wazuh indexer is built on OpenSearch, which fails to start with Ubuntu's default memory-map limit. I raised it and made the change survive reboots, so the stack wouldn't break the next time the server restarted.

    Ubuntu host
    sudo sysctl -w vm.max_map_count=262144
echo "vm.max_map_count=262144" | sudo tee -a /etc/sysctl.conf

  2. Opened only the ports Wazuh needs

    I kept UFW on and allowed four things: SSH for me, the dashboard, and the agents' event and enrolment ports. Everything else stays closed, which keeps the monitoring server from becoming a weak point itself.

    Ubuntu host
    sudo ufw allow OpenSSH
sudo ufw allow 443/tcp     # dashboard
sudo ufw allow 1514/tcp    # agent events
sudo ufw allow 1515/tcp    # agent enrolment
sudo ufw enable
sudo ufw status numbered

  3. Deployed the stack from a pinned release

    I used Wazuh's official single-node Compose project and pinned a release tag. That keeps the manager and agent versions matched, because mismatched versions are a common reason agents fail to connect.

    Ubuntu host
    git clone https://github.com/wazuh/wazuh-docker.git -b v4.9.2
cd wazuh-docker/single-node
docker compose -f generate-indexer-certs.yml run --rm generator
docker compose up -d
docker compose ps

    The certificate step comes first because the three containers talk to each other over TLS. Once all three showed running, I signed in at https://<server-ip> and changed the default admin password straight away.

  4. Enrolled the Windows laptop

    In an administrator PowerShell window, I installed the agent silently, pointed it at the manager, and gave it a name I would recognise in alerts.

    Windows, PowerShell as administrator
    Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.9.2-1.msi -OutFile $env:tmp\wazuh-agent.msi
msiexec.exe /i $env:tmp\wazuh-agent.msi /q WAZUH_MANAGER='192.168.1.50' WAZUH_AGENT_NAME='win-laptop-01'
NET START WazuhSvc

  5. Enrolled the Mac

    macOS reads the manager address from an environment file during installation. I used the arm64 package for Apple silicon. Intel Macs need intel64.

    macOS Terminal
    curl -so wazuh-agent.pkg https://packages.wazuh.com/4.x/macos/wazuh-agent-4.9.2-1.arm64.pkg
echo "WAZUH_MANAGER='192.168.1.50' && WAZUH_AGENT_NAME='mac-01'" > /tmp/wazuh_envs
sudo installer -pkg ./wazuh-agent.pkg -target /
sudo /Library/Ossec/bin/wazuh-control start

  6. Tested it with an attack I controlled

    A SIEM that has never caught anything hasn't been proven to work. So I caused an event I knew it should catch: I locked the Windows laptop and typed a wrong password several times. Windows logs each attempt as event ID 4625, the agent forwards it, and Wazuh rule 60122 fires. I then filtered for those alerts in Threat Hunting:

    Dashboard search
    agent.name:win-laptop-01 and rule.id:60122

    For each alert I read three fields: data.win.eventdata.targetUserName, data.win.eventdata.ipAddress and the timestamp. Those answer who was targeted, from where, and when, which is the first thing I write in any triage note.

  7. Compared it with Microsoft Defender

    Finally, I opened the Defender portal for the same device and time window to see what each tool recorded.

What I found

  • Every failed logon from the test reached the dashboard as a rule 60122 alert, with the user, source and time attached. That proved the whole chain worked, from the endpoint to the agent, manager, indexer and dashboard.
  • Defender didn't treat a few wrong passwords as a threat, while Wazuh kept every attempt as an event. The two tools answer different questions. Defender blocks known threats, and the SIEM keeps the history you need to spot patterns such as repeated failures across several machines.
  • The two things most likely to break this setup are the indexer's memory limit and blocked agent ports. Getting both right first saved more time than any later step.
If you seeCause and fix
The indexer container keeps restartingvm.max_map_count is too low. Raise it as in step 1, then run docker compose restart.
An agent is stuck on Never connectedPort 1514 or 1515 is blocked, or the manager IP is wrong. Test with Test-NetConnection 192.168.1.50 -Port 1514.
The browser shows a certificate warningThis is expected with self-signed lab certificates. Use a proper certificate before exposing the dashboard beyond the lab.

What I'd do next

  • Write a custom rule that alerts when the same account fails on more than one machine within ten minutes, a pattern a single laptop can't see.
  • Send alerts to email or Slack so nobody has to watch the dashboard.
  • Replace the self-signed certificates and put the dashboard behind a VPN.
