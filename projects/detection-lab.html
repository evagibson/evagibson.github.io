Detecting attacks and finding vulnerabilities with Splunk and OpenVAS

In my home lab, I contained a vulnerable machine with firewall rules, sent Windows logs to Splunk to hunt for attacks, and scanned the target with OpenVAS.

Role it supports
SOC Analyst, Security / DevSecOps
Setting
Home lab
Tools
pfSense, Splunk, Universal Forwarder, Kali, OpenVAS, Metasploitable 2

The problem

A network is only secure if someone can see what happens on it and knows where its weak spots are. Using the home lab I built in Project 01, I set out to do the SOC side: contain risky machines with firewall rules, collect Windows logs centrally so attacks show up, and scan for vulnerabilities before an attacker finds them.

What I built

Three security layers on top of the lab network. pfSense rules keep the vulnerable Metasploitable 2 machine contained. The Windows machines forward their event logs to Splunk, where I hunt for attacks. OpenVAS on Kali scans the target for known vulnerabilities.

What it runs on: the eight-VM lab from Project 01, plus Splunk Enterprise (trial), the Splunk Universal Forwarder, and Greenbone OpenVAS on Kali.

SafetyMetasploitable 2 is vulnerable on purpose. I kept it on the attack-lab VLAN, never bridged it to my home network, and never exposed it to the internet.

How I did it

  1. Locked down traffic between VLANs

    pfSense blocks traffic on new interfaces by default, and I kept it that way, adding only the connections each zone needs. I built the rules on VLAN 10 first, then copied each one to VLAN 20 and VLAN 30 and changed the source, which kept the three rule sets consistent.

    InterfaceRuleWhy
    All VLANsAllow DNS to the VLAN's own gatewayName resolution
    VLAN 10Allow to Splunk TCP 9997 and 8000Send logs, open the Splunk web page
    VLAN 30Allow Kali to Metasploitable 2Scanning and testing the target
    VLAN 30Block Metasploitable 2 to any other VLANThe vulnerable host stays contained
    All VLANsBlock to other private networks, then allow internetUpdates without lateral movement

    To prove the segmentation worked, I checked that Metasploitable 2 could not ping 10.10.10.1, while Kali could still reach 10.10.30.8.

  2. Set up Splunk to receive logs

    On the Ubuntu desktop VM in VLAN 20, built in Project 01, I installed Splunk Enterprise from its .deb package and set it to start on boot.

    Ubuntu, Splunk server
    sudo dpkg -i splunk-*-linux-amd64.deb
sudo /opt/splunk/bin/splunk start --accept-license
sudo /opt/splunk/bin/splunk enable boot-start

    In Settings → Forwarding and receiving, I added receiving port 9997. In Settings → Indexes, I created an index called wineventlog so Windows events are kept apart and are quicker to search.

  3. Forwarded the Windows logs

    On Windows 10 and Windows Server, I installed the Splunk Universal Forwarder and pointed it at the Splunk server on port 9997. The installer sends logs to the default index, so I added this file to route Security and System events to wineventlog, then restarted the forwarder.

    C:\Program Files\SplunkUniversalForwarder\etc\system\local\inputs.conf
    [WinEventLog://Security]
index = wineventlog
disabled = 0

[WinEventLog://System]
index = wineventlog
disabled = 0
    Windows, PowerShell as administrator
    Restart-Service SplunkForwarder

  4. Hunted for failed logons

    To prove logs were flowing, I typed a wrong password several times on Windows 10, then searched for event 4625 in Splunk:

    Splunk search
    index=wineventlog EventCode=4625
| stats count by host, Account_Name
| sort - count

  5. Scanned Metasploitable 2 with OpenVAS

    On Kali, I installed Greenbone (OpenVAS). Setup prints a password for the admin user, which I stored safely and kept out of every screenshot.

    Kali
    sudo apt update && sudo apt install -y gvm
sudo gvm-setup
sudo gvm-check-setup
sudo gvm-start

    In the web interface at https://127.0.0.1:9392, I added 10.10.30.8 under Configuration → Targets, then created and ran a Full and fast scan task for it under Scans → Tasks.

What I found

  • The firewall held. Metasploitable 2 couldn't reach the user or server VLANs, so even a fully compromised machine stays contained.
  • Failed logons on Windows 10 showed up in Splunk with the host and account, proving the full log path from endpoint to SIEM.
  • OpenVAS flagged many high-severity issues on Metasploitable 2, as expected for a machine built to be vulnerable. For the most severe ones I recorded the service, the CVE, and the recommended fix, because a scan report is only useful once each finding has an explanation and a fix behind it.
  • Starting from "deny everything" and adding rules one at a time made every allowed connection a decision I could explain.
If you seeCause and fix
No events in SplunkThe firewall rule for 9997 is missing, or receiving isn't enabled. Check splunkd.log on the forwarder.
OpenVAS shows no resultsThe feeds are still syncing after setup. Run sudo gvm-check-setup and wait for it to pass.

What I'd do next

  • Attack Metasploitable 2 from Kali and check which steps Splunk and pfSense logs reveal, then write detections for the gaps.
  • Send pfSense firewall logs to Splunk, so blocked traffic between VLANs raises an alert.
  • Turn the worst OpenVAS findings into a report a developer or system owner can act on, then rescan after their fixes to confirm each issue is closed.
