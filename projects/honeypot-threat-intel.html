Turning honeypot attacks into STIX threat intelligence

My MSc thesis pipeline: real SSH attacks captured by Cowrie, grouped into sessions, mapped to MITRE ATT&CK, and published as a validated STIX 2.1 bundle.

Role it supports
Threat Intel / SOC Analyst, Python Developer
Setting
MSc thesis, live cloud honeypot
Tools
T-Pot, Cowrie, Python, stix2, jq

The problem

Honeypots attract a steady stream of real attacks, but the raw logs are just lines of JSON that nobody outside the lab can use. For my MSc thesis I set out to turn those logs into threat intelligence another team could load and act on: which IP addresses attacked, what they tried, and which MITRE ATT&CK techniques that matches.

What I built

A pipeline in five stages. A T-Pot honeypot on a cloud VM captured real SSH and Telnet attacks with Cowrie. A Python script grouped the events into attacker sessions, mapped them to ATT&CK, and wrote a STIX 2.1 bundle, which I then validated.

What it runs on: a separate cloud VM (Debian 12, 8 GB RAM, public IP) with nothing else on it, left running for several days to collect events, plus Python 3.10 or later on my own machine for the analysis.

SafetyI kept the honeypot on its own cloud VM, away from any network with real data, and limited the provider firewall to what T-Pot needs. Anyone repeating this should do the same and delete the VM afterwards.

How I did it

  1. Deployed T-Pot

    I chose T-Pot because it bundles Cowrie and other honeypots in Docker with a ready-made dashboard. I ran the installer as a normal user with sudo rights, as the project requires, and picked the Hive install.

    Honeypot VM
    git clone https://github.com/telekom-security/tpotce
cd tpotce
./install.sh
sudo reboot

    After the reboot, my own SSH moved to port 64295, leaving port 22 to the honeypot, and the T-Pot web interface came up on https://<vm-ip>:64297.

  2. Collected the Cowrie log

    Cowrie writes one JSON event per line. I copied the file off the VM so the analysis never ran on an exposed machine.

    Your machine
    scp -P 64295 user@<vm-ip>:~/tpotce/data/cowrie/log/cowrie.json .
head -n 3 cowrie.json

    The events I used were cowrie.login.failed, cowrie.login.success, cowrie.command.input and cowrie.session.file_download. Every event carries a session ID, which is how I grouped them.

  3. Set up an isolated Python environment

    I pinned the validator to 3.2.0, because version 3.3.1 is published without its schema files and fails on every bundle.

    Your machine
    python3 -m venv .venv
source .venv/bin/activate
pip install stix2 "stix2-validator==3.2.0"   # 3.3.1 ships without its schemas

  4. Grouped events into sessions and mapped them to ATT&CK

    The script reads every event, groups them by session, and writes one STIX Observed Data object per session. I kept the mapping to two simple rules that anyone can check. Repeated failed logins in one session mean T1110 Brute Force. A download, or a wget, curl or tftp command, means T1105 Ingress Tool Transfer.

    build_bundle.py
    import json
from collections import defaultdict
from stix2 import (AttackPattern, Bundle, ExternalReference, Indicator,
                   IPv4Address, ObservedData, Relationship)

FAILED_LOGIN_THRESHOLD = 5   # tune this to your data

def technique(name, tid):
    return AttackPattern(name=name, external_references=[ExternalReference(
        source_name="mitre-attack", external_id=tid,
        url=f"https://attack.mitre.org/techniques/{tid}/")])

brute_force = technique("Brute Force", "T1110")
tool_transfer = technique("Ingress Tool Transfer", "T1105")
objects = [brute_force, tool_transfer]

sessions = defaultdict(list)
with open("cowrie.json") as f:
    for line in f:
        event = json.loads(line)
        sessions[event["session"]].append(event)

for events in sessions.values():
    src = events[0]["src_ip"]
    times = sorted(e["timestamp"] for e in events)
    ip = IPv4Address(value=src)
    observed = ObservedData(first_observed=times[0], last_observed=times[-1],
                            number_observed=len(events), object_refs=[ip.id])
    objects += [ip, observed]

    failed = sum(e["eventid"] == "cowrie.login.failed" for e in events)
    commands = " ".join(e.get("input", "") for e in events
                        if e["eventid"] == "cowrie.command.input")
    downloaded = any(e["eventid"] == "cowrie.session.file_download" for e in events)

    for matched, attack in (
        (failed >= FAILED_LOGIN_THRESHOLD, brute_force),
        (downloaded or any(t in commands for t in ("wget ", "curl ", "tftp ")), tool_transfer),
    ):
        if matched:
            indicator = Indicator(name=f"{attack.name} from {src}",
                                  description=f"Seen on the Cowrie honeypot in {len(events)} events",
                                  pattern_type="stix",
                                  pattern=f"[ipv4-addr:value = '{src}']",
                                  valid_from=times[0])
            objects += [indicator,
                        Relationship(indicator, "indicates", attack),
                        Relationship(indicator, "based-on", observed)]

bundle = Bundle(objects=objects, allow_custom=False)
with open("bundle.json", "w") as f:
    f.write(bundle.serialize(pretty=True))
print(f"{len(sessions)} sessions, {len(objects)} STIX objects")
    Your machine
    python build_bundle.py

  5. Validated the bundle

    Threat-intel platforms reject malformed STIX, so I validated the bundle before calling it done.

    Your machine
    stix2_validator bundle.json

    The validator reported STIX JSON: Valid, with only advisory warnings about reference hashes. I also followed indicators through their indicates relationships to confirm each one pointed at T1110 or T1105.

  6. Read the results like an analyst

    Finally, I counted which source IPs appeared most and which commands attackers ran after logging in. Those two lists are what a SOC turns into block rules and detection ideas.

    Your machine
    jq -r 'select(.eventid=="cowrie.login.failed") | .src_ip' cowrie.json | sort | uniq -c | sort -rn | head
jq -r 'select(.eventid=="cowrie.command.input") | .input' cowrie.json | sort | uniq -c | sort -rn | head

What I found

ATT&CK techniques detectedT1110 Brute Force, T1105 Ingress Tool Transfer
  • Grouping by session turned thousands of events into a few hundred stories an analyst can actually read.
  • Brute-force logins and attempts to download tools onto the server were the two behaviours worth mapping, which is why the bundle covers T1110 and T1105.
  • Simple, explainable mapping rules are easier to defend than clever ones, and ATT&CK IDs let anyone check them.

What I'd do next

  • Enrich each attacking IP with its country and network owner, so the intelligence shows where attacks come from.
  • Map more techniques, such as discovery commands like uname -a to T1082 System Information Discovery.
  • Push the bundle to a sharing platform such as MISP or OpenCTI, so other teams receive it automatically.
