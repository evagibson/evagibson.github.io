Testing a point-of-sale app with Playwright

Test cases written from requirements, then automated UI and API checks for login, access control and input validation, running on every push.

Role it supports
QA Engineer, Security Tester, Junior Developer
Setting
My own app, in progress
Tools
Playwright, JavaScript, Node.js, GitHub Actions

The problem

I'm building a stock and point-of-sale web app with a REST API and a database. A till that miscounts stock, or lets a cashier into the admin pages, is a real business risk. Checking every flow by hand before each release is slow and easy to get wrong, so I needed tests that run on their own every time the code changes.

What I built

A test suite I approach the way I test production software at work: manual test cases first, then automated Playwright checks for the flows that must never break, with a security focus on login, access control and input validation. GitHub Actions runs the suite in three browsers on every push.

The test cases behind it

I wrote these before any automation. Each one has an expected result, so a pass or a fail is never a matter of opinion.

IDScenarioExpected resultType
AUTH-01Cashier signs in with valid detailsLands on the till screenFunctional
AUTH-02Sign in with a wrong passwordGeneric error that doesn't say which field was wrongSecurity
AUTH-03Cashier opens /admin directlyAccess denied, no admin data shownAccess control
API-01Call GET /api/products with no token401 UnauthorizedSecurity
API-02Record a sale with quantity -1400 Bad Request, stock unchangedInput validation
SALE-01Sell 2 of an item with 10 in stockStock shows 8Regression

What it runs on: Node.js 20 or later, the app running locally or on a test server, and two test accounts (a cashier and an admin). The routes, labels and messages in the code match my app. Anyone reusing it should change them to match theirs.

How I did it

  1. Added Playwright to the project

    Project folder
    npm init playwright@latest

    I chose JavaScript, a tests folder, and the GitHub Actions workflow. Then I set a base URL so tests use short paths, and turned on traces and failure screenshots so every failed test comes with evidence.

    playwright.config.js (excerpt)
    use: {
  baseURL: process.env.BASE_URL || 'http://localhost:3000',
  trace: 'on-first-retry',
  screenshot: 'only-on-failure',
},

  2. Automated the login and access-control cases

    A shared sign-in helper keeps each test short. AUTH-02 checks that the error doesn't reveal whether the email or the password was wrong, which would help an attacker. AUTH-03 checks that the server refuses the admin page, not just that the menu hides it.

    tests/auth.spec.js
    const { test, expect } = require('@playwright/test');

async function signIn(page, email, password) {
  await page.goto('/login');
  await page.getByLabel('Email').fill(email);
  await page.getByLabel('Password').fill(password);
  await page.getByRole('button', { name: 'Sign in' }).click();
}

test('AUTH-01 cashier can sign in', async ({ page }) => {
  await signIn(page, process.env.CASHIER_EMAIL, process.env.CASHIER_PASSWORD);
  await expect(page).toHaveURL(/\/pos/);
});

test('AUTH-02 wrong password shows a generic error', async ({ page }) => {
  await signIn(page, process.env.CASHIER_EMAIL, 'not-the-password');
  await expect(page.getByRole('alert')).toHaveText('Invalid email or password');
});

test('AUTH-03 cashier cannot open the admin page', async ({ page }) => {
  await signIn(page, process.env.CASHIER_EMAIL, process.env.CASHIER_PASSWORD);
  const response = await page.goto('/admin');
  expect([401, 403]).toContain(response.status());
  await expect(page.getByText('Manage users')).toHaveCount(0);
});

  3. Automated the API cases

    I used Playwright's request fixture to call the API directly. It's faster than going through the UI, and it tests the server's own checks, which an attacker can reach without the UI at all.

    tests/api.spec.js
    const { test, expect } = require('@playwright/test');

test('API-01 products need a token', async ({ request }) => {
  const res = await request.get('/api/products');
  expect(res.status()).toBe(401);
});

test('API-02 negative quantity is rejected', async ({ request }) => {
  const login = await request.post('/api/login', {
    data: { email: process.env.CASHIER_EMAIL, password: process.env.CASHIER_PASSWORD },
  });
  const { token } = await login.json();
  const res = await request.post('/api/sales', {
    headers: { Authorization: `Bearer ${token}` },
    data: { productId: 1, quantity: -1 },
  });
  expect(res.status()).toBe(400);
});

  4. Ran the suite and read the report

    Test accounts live in environment variables, never in the code.

    Project folder
    export CASHIER_EMAIL=cashier@test.local CASHIER_PASSWORD='...'
npx playwright test
npx playwright show-report

  5. Ran it on every push

    The workflow Playwright generated runs the suite in GitHub Actions. I stored the test accounts as repository secrets and passed them to the test step.

    .github/workflows/playwright.yml (test step)
    - name: Run Playwright tests
  run: npx playwright test
  env:
    BASE_URL: ${{ secrets.BASE_URL }}
    CASHIER_EMAIL: ${{ secrets.CASHIER_EMAIL }}
    CASHIER_PASSWORD: ${{ secrets.CASHIER_PASSWORD }}

  6. Reported failures so they get fixed

    When a test fails, I write a defect report a developer can reproduce without asking me anything. This is the format I use, shown with an example of the kind of issue AUTH-03 exists to catch.

    FieldExample
    TitleCashier can open /admin by typing the URL
    SeverityHigh: access control bypass
    Steps1. Sign in as a cashier. 2. Go to /admin.
    Expected403 and no admin data
    ActualAdmin dashboard loads with the user list
    EvidencePlaywright trace, screenshot, test AUTH-03

What I found

  • Writing the expected result before automating kept each test honest. A test can't quietly pass by checking the wrong thing.
  • Testing the API directly covers security gaps the UI can hide, such as a missing token check behind a hidden button.
  • With the suite running on every push, a broken login or stock count shows up in the pull request before it reaches the till.

What I'd do next

  • Add tests for the sales and stock flows, starting with SALE-01, and for roles beyond cashier and admin.
  • Run an OWASP ZAP baseline scan in the same pipeline to catch common web vulnerabilities automatically.
  • Add mobile viewport runs, since cashiers may use tablets at the till.
